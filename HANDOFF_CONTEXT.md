I'm continuing work on SmartFlow NLEX, my capstone traffic-forecasting dashboard. The frontend is Next.js in Front-End-Dashboard/ running on port 3002, the backend is Express + TypeScript in Back-End/ running on port 4000 via npm run dev with tsx watch, and the data lives in an AWS RDS Postgres instance at smartflow-db.choym2mcymec.ap-southeast-1.rds.amazonaws.com, database nlex_capstone, user postgres. The password is in my own notes and in retrain_honest.py — don't commit it anywhere.

The single source of truth for volume is gold.daily_traffic_volume_corrected, which holds 2,398 days spanning 2020-01-01 to 2026-07-25. Forecast rows live in gold.ml_predictive_volume with is_holdout and is_future flags, and model scores live in gold.ml_model_metrics. The authoritative 20-exit NLEX reference is enforced through gold.exit_name_map and gold.exit_direction_role. Be careful with nlex_traffic_volume, which feeds the Descriptive tab — it is a completely different dataset with only 17 plazas, Entries only, averaging 1,240,938 vehicles a day against gold's 1,348,845. Those two have never been reconciled, so never mix them or treat one as a check on the other.

The train/holdout split is verified and correct: training covers 2020-01-01 to 2025-04-05, which is 1,922 days or 80.15 percent; the holdout covers 2025-04-06 to 2026-07-25, which is 476 days or 19.85 percent; and there are 28 projected future days from 2026-07-26 to 2026-08-22. That totals 2,398 days. This matters because the chart windows the past according to a 3-month, 12-month or all-history range selector, so the blue "Past" band on screen is usually showing only the last few hundred days of a five-year training set, not the whole 80 percent. That confusion has already cost me time once.

Training runs through retrain_honest.py, which replaced an earlier pipeline that was fundamentally invalid — it had sabotaged configs, data leakage, and a horizon mismatch between what was scored and what was served. The honest pipeline uses rolling-origin walk-forward validation with HORIZON=14, STEP=14 for non-overlapping blocks, N_ORIGINS=34, SEASON=7, FUTURE_DAYS=28 and CTX=0. Weather columns are avg_temp, total_rain, avg_wind and avg_humidity, and only SARIMAX, Prophet and LSTM consume them — Holt-Winters and Holts Linear are univariate and have no weather variant at all. The checkpoint fingerprint includes a hash of the data so a corrected dataset properly invalidates stale checkpoints.

The real results over 476 scored days and 34 origins are as follows, and these are the only numbers that should ever appear in the dashboard. Prophet_nw leads at 9.76 percent WMAPE with MASE 0.829 and R-squared 0.5913, accepted at rank 1. Prophet follows at 9.81 percent, MASE 0.833, R-squared 0.5881, accepted at rank 2. Holt-Winters is rejected at 12.05 percent, MASE 1.023, R-squared 0.3276. SARIMAX is rejected at 12.68 percent, MASE 1.076, R-squared 0.2508. LSTM is rejected at 16.18 percent, MASE 1.374, R-squared -0.0023. Holts Linear is rejected at 16.99 percent, MASE 1.443, R-squared -0.0468. The headline finding is that weather does not help — the top-ranked model is the weather-free one, and this held across four separate configurations and survived a 78 percent correction to the underlying volume figures.

Several bugs have already been found and fixed, and I don't want them reintroduced. MASE must be computed against a lag-7 seasonal naive baseline using ins[7:] - ins[:-7], not np.diff(x, n=7), which is a seventh-order difference and produced a nonsense MASE of about 0.011. MASE is a ratio and must never be displayed as a percentage. The uses_weather flag must come from an explicit set of weather-consuming models, not from checking whether a name ends in "_nw", because that wrongly marked Holt-Winters as weather-aware. The x-axis category values must include the year, because duplicate labels like three separate "Aug 9" entries break markArea and markLine zone anchoring and silently send click-to-drill to the wrong day. The dataZoom control must stay slider-only, since type "inside" swallows clicks and breaks drill-down. And rejection reasons must name the criterion that actually failed — Holt-Winters fails on MASE, not on WMAPE, and the UI once claimed otherwise.

Most of the recent work has been on making the forecast chart readable. In PredictiveVolumeChart.tsx I added a centeredMean helper that draws a centred 7-day rolling mean of the actuals as a bold line, so the smooth 14-day-ahead forecast finally has a like-for-like series to be compared against instead of a raw daily noise band. It derives every value from real observations already in the series and invents nothing, the raw daily line stays visible underneath at 0.13 opacity, and it is deliberately centred rather than trailing because a trailing mean would shift the curve about three days right and falsely suggest the forecast leads or lags. Smoothing only applies when the data isn't already aggregated and there are more than 120 points, since weekly and monthly buckets are already means and smoothing them again would be double-averaging. The default granularity moved from Daily to Weekly because roughly 880 daily points across 1400 pixels was unreadable. The actual line was recoloured to a neutral slate, #334155 in light mode and #cbd5e1 in dark, because it previously clashed with the sky-blue rainfall bars. The rainfall axis headroom went from value.max times 1.2 to times 4, which confines rain to the bottom quarter of the plot instead of letting it span roughly 83 percent and cut through the volume lines. And the zone legend now states the true split, reading something like "Past 1,922d trained · 80.15% · showing last 365d" so the windowing is explicit.

Other frontend pieces worth knowing about: WeatherEvidencePanel.tsx is a collapsible panel that answers why only rainfall is plotted, showing that humidity actually correlates about twice as strongly and that all four variables are model inputs, and it fetches /api/traffic/weather-evidence. ModelNarrative.tsx is template-based natural language generation and explicitly not an LLM — every sentence is composed from gold.ml_model_metrics at render time with no stored prose and no hardcoded figures. aggregateSeries.ts handles weekly and monthly bucketing where buckets carry the mean daily volume rather than the sum and zones are assigned by majority; Yearly was removed because 28 future days disappear inside a year-long bucket. useThemeTokens.ts reads CSS custom properties at runtime because ECharts cannot resolve var() and the chart otherwise stayed on the light palette in dark mode.

On the backend, traffic.service.ts gained getWeatherEvidenceFromDb for the correlations and the with/without model comparison, and getSplitSummary which counts train, holdout and future days over the unwindowed table so the chart can distinguish what was trained on from what is currently drawn — it's exposed to the frontend as data.split. The forecast range query anchors on the holdout start date rather than the newest row, because anchoring on the newest row meant every preset shorter than the holdout ate the entire history and returned zero past rows.

Still open: the Descriptive versus Predictive source reconciliation between the 17-plaza and 20-exit datasets; audit_logs.user_id still records "dashboard" because the frontend doesn't send an x-user header; /api/audit-log/list and /api/audit-log/analytics are publicly readable with no auth; bronze.nlex_traffic_volume.avg_speed_kmh is negative in 20.6 percent of rows; a stale out/ static export still contains a Mapbox placeholder token; and there's no orchestration layer, which was deliberately left out of scope. Two optional improvements I've considered are plotting the seasonal-naive baseline so MASE has a visual counterpart, and moving rainfall into its own ECharts sub-grid instead of sharing the main plot area.

Finally, the rules I work by. Never invent, estimate or interpolate a number — every figure must trace back to the database or the pipeline output, and if something is missing say so rather than filling it in. Do not remove the Past, Present and Future holdout zones, the granularity toggles, the model toggles or the Weather toggle; those bands live on the raw actual series via markArea, so hiding that series would take the zones with it. Verify claims against the database before asserting them, and tell me plainly and directly when something is wrong rather than softening it. And MASE is never a percentage.
